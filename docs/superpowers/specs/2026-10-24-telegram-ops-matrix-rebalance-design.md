> **Дата создания:** 24.10.2026  
> **Статус:** Утверждён пользователем

---

## 1. Обзор и Цели

### 1.1. Назначение системы
Превращение работающего в фоновом режиме Telegram-бота в полноценный удалённый пульт управления дельта-нейтральной фермой (Hedge Ops Terminal). Пользователь со смартфона получает возможность:
1. Запрашивать каноническую матрицу рынка с расчётом потерь на вход маркетом (`/o`) и выход (`/c`) по живым ончейн-балансам.
2. Проверять баланс сетей и получать готовые инструкции по ребалансировке/бриджу между Robinhood Chain и Arbitrum zkLighter (`/b`).
3. Фиксировать открытие новых позиций (`/o <TICKER>`), автоматически активируя их в `config.json` и запуская круглосуточный монитор защиты от ликвидаций.
4. Фиксировать закрытие позиций (`/c <TICKER>`), мгновенно выключая алерты и сирену по ним в `config.json`.
5. Автоматически протоколировать реальные ончейн-затраты на спред и итоговый PnL в каноническую таблицу `pnl_and_points_analysis.csv`.

### 1.2. Ключевые требования и ограничения
* **Непрерывность мониторинга:** Фоновый 15-секундный цикл опроса цен и бот-сирена критических ликвидаций (`index.ts`) не должны блокироваться во время выполнения долгих расчётов команд.
* **Zero Stale Balances:** Балансы кошельков запрашиваются ончейн в секунду вызова команд. Запрещено использовать статические цифры.
* **Мобильный Telegram UX:** Текстовое сообщение строго ограничено 4096 символами. В чат выводятся ончейн-шапка, структурированный ТОП-5 рекомендаций и экспертный вердикт. Полная матрица на все 27 инструментов отправляется файлом-документом `market_matrix.md`.
* **Anti-Sybil безопасность:** Никаких закрытых ключей; запросы выполняются к публичным API и индексаторам.

## 3. Спецификация Команд Telegram-бота

### 3.1. Команда `/b [w1/w2]` — Бридж и Ребалансировка
* **Назначение:** Определение перекоса капитала между Robinhood Chain и Arbitrum zkLighter и расчет точной суммы бриджа для восстановления пропорции 50/50.
* **Алгоритм:**
  1. Выполняются живые запросы к API обеих сетей для W1 (`0xf5FC...aF7f`) и W2 (`0x1F14...3Ff2`):
     - Robinhood: `GET https://api.rh.lighter.xyz/api/v1/account?by=l1_address&value={address}`
     - Arbitrum: `GET https://mainnet.zklighter.elliot.ai/api/v1/account?by=l1_address&value={address}`
  2. Парсятся поля `total_asset_value` (общий капитал) и `collateral` / свободные средства.
  3. Для каждого кошелька вычисляется:
     $$\text{Total Equity} = \text{RH Equity} + \text{Arb Equity}$$
     $$\text{Target per Leg} = \frac{\text{Total Equity}}{2}$$
     $$\Delta_{\text{skew}} = \text{RH Equity} - \text{Arb Equity}$$
  4. Формируется рекомендация:
     - Если $\Delta_{\text{skew}} > 0$: Перевести **\$$(\Delta_{\text{skew}} / 2)\$$** из **Robinhood Chain** в **Arbitrum zkLighter**.
     - Если $\Delta_{\text{skew}} < 0$: Перевести **\$$(\|\Delta_{\text{skew}}\| / 2)\$$** из **Arbitrum zkLighter** в **Robinhood Chain**.
     - Если на аккаунте есть открытая позиция, бот указывает максимальную сумму, доступную для безопасного вывода без риска ликвидации.

---

### 3.2. Команда `/o` (без аргументов) — Сканирование рынка и Поиск входа
* **Назначение:** Анализ рынка по 27 общим инструментам Lighter, расчет потерь на вход маркетом и формирование рекомендаций.
* **Алгоритм Orderbook Walk на вход (Вектор: RH Short + Arb Long):**
  1. Берутся актуальные депозиты W1 и W2. Рассчитывается динамический номинал под 7x плечо:
     $$\text{Notional}_{100\%} = \frac{\text{Total Equity}}{2} \times 7, \quad \text{Notional}_{50\%} = \frac{\text{Total Equity}}{4} \times 7$$
  2. Запрашиваются стаканы (глубина 50 уровней) по всем общим инструментам:
     - Robinhood Chain: `rhBids` (продажа в биды)
     - Arbitrum zkLighter: `arbAsks` (покупка из асков)
  3. Для каждого актива эмулируется поглощение стакана до достижения суммы $\text{Notional}_{100\%}$ и $\text{Notional}_{50\%}$:
     $$\text{Loss} = (\bar{P}_{\text{Arb Buy}} - \bar{P}_{\text{RH Sell}}) \times \text{BaseQty}$$
     $$\text{Loss \%} = \frac{\text{Loss}}{\text{Notional}} \times 100\%$$
  4. Читается `earnings_calendar.json` для выявления акций с Earnings Boost на текущей неделе.
  5. Сортировка выполняется **СТРОГО ПО ВОЗРАСТАНИЮ `OI Robinhood ($) 🟢`**.
  6. **Формат ответа в Telegram:**
     - Текстовое сообщение: Живые ончейн-балансы W1/W2, ТОП-5 карточек рекомендаций с обязательным выводом **Потерь 100% и 50%**, **OI Robinhood ($) 🟢**, **OI Arbitrum ($)**, стенок L1/L2 и вердикта.
     - Документ: Файл `market_matrix.md`, содержащий полную каноническую таблицу по всем 27 активам.

---

### 3.3. Команда `/c` (без аргументов) — Расчёт потерь на Закрытие
* **Назначение:** Оценка затрат на мгновенный выход маркетом из открытых позиций портфеля.
* **Алгоритм Orderbook Walk на выход (Вектор: RH Buy + Arb Sell):**
  1. Из `config.json` считываются активные связки (например, $META и $PLTR).
  2. Запрашиваются стаканы:
     - Robinhood Chain: `rhAsks` (откуп шорта из асков)
     - Arbitrum zkLighter: `arbBids` (продажа лонга в биды)
  3. Для фактического размера контрактов каждой позиции рассчитывается реальное проскальзывание и потери в $ при закрытии прямо сейчас.
  4. Формируется отчет:
     - Сводка по текущим открытым позициям (сколько $ сгорит на спреде выхода).
     - Сводная матрица потерь на выход для остальных инструментов.

---

### 3.4. Команда `/o <TICKER> [w1/w2]` — Фиксация открытия и Активация мониторинга
* **Назначение:** Привязка новой сделки, расчет затрат на вход и включение фонового мониторинга.
* **Алгоритм:**
  1. Опрос кошельков: бот проверяет W1 и W2 (или указанный в аргументе) через Lighter Positions API.
  2. Извлечение фактических данных: `entryPrice` (RH и Arb), `size`, `margin`, фактическое плечо $L$.
  3. Вычисление потерь на входе:
     $$\text{Entry Friction} = (P_{\text{entry}}^{\text{Arb Long}} - P_{\text{entry}}^{\text{RH Short}}) \times \text{Size}$$
  4. Модификация `config.json`:
     - Для найденной связки выставляется `"active": true`.
     - Записываются точные `entryPrice`, `margin`, `leverage`, `size`, `liquidationPrice`.
     - Фоновый монитор подхватывает изменения в течение 15 секунд и включает сирену ликвидаций.
  5. Запись в `pnl_and_points_analysis.csv`:
     - Добавляются строки сделки с фиксацией выделенной маржи и понесенного входного трения стакана.
  6. Отправка подтверждающей карточки в Telegram.

---

### 3.5. Команда `/c <TICKER> [w1/w2]` — Фиксация закрытия и Остановка мониторинга
* **Назначение:** Отключение алертов по закрытой сделке и протоколирование финансового результата.
* **Алгоритм:**
  1. Модификация `config.json`:
     - Для указанного тикера выставляется `"active": false`.
     - **Мониторинг и сирена по этой паре мгновенно останавливаются.**
  2. Ончейн-аудит закрытия:
     - Запрос балансов кошелька после закрытия (`endingBalance`).
     - Расчет $\text{Net Price PnL}$ и чистого изменения баланса ($\text{Net Balance Change}$).
  3. Запись в `pnl_and_points_analysis.csv`:
     - Фиксация закрывающих строк в каноническом формате журнала (цены выхода, PnL, результат недели).
  4. Отправка отчета о закрытии в Telegram.

## 5. Доставка Файлов в Telegram (`sendDocument`)

В класс `TelegramBotService` ([src/bot/telegram.ts](file:///c:/$OFT/_Vibecoding/Lighter-poly/src/bot/telegram.ts)) добавляется метод `sendDocument(chatId, filename, contentBuffer, caption)` через стандартный multipart-запрос к Telegram Bot API:
```typescript
POST https://api.telegram.org/bot<TOKEN>/sendDocument
```
Это гарантирует, что пользователь всегда получит полный markdown-отчет без ограничений по длине и сможет просмотреть его прямо внутри Telegram.
